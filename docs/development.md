# توسعه و اجرای محلی

[فهرست مستندات](README.md)

## پیش‌نیاز و نصب

نسخهٔ Node باید حداقل `22.13.0` باشد؛ `node:sqlite` در آداپتور و اسکریپت مهاجرت استفاده می‌شود. نسخه‌های نصب‌شده را `package-lock.json` تعیین می‌کند. `npm ci` نصب تکرارپذیر انجام می‌دهد. تنظیمات CLI و ساخت در `scripts/run-framework.mjs`، `scripts/build-node.mjs` و `vite.config.ts` قرار دارند.

```sh
npm ci
cp .env.example .env.local
mkdir -p "$PWD/data/media"
```

در `.env.local`، `MVP_RUNTIME=node`، مسیر مطلق فایل پایگاه داده زیر پوشهٔ `data`، مسیر مطلق `data/media` و `APP_ORIGIN=http://localhost:5173` را وارد کنید. خود پوشهٔ والد پایگاه داده باید وجود داشته باشد. اطلاعات محرمانه و فایل‌های داده را وارد Git نکنید.

مقادیر را پیش از اجرای فرمان‌ها به محیط فرآیند صادر کنید؛ اسکریپت مهاجرت و سرور standalone خواندن خودکار فایل env را تضمین نمی‌کنند. برای فایل مورد اعتماد با نحو سازگار با shell:

```sh
set -a
. ./.env.local
set +a
npm run db:migrate:node
npm run dev
```

مهاجرت‌ها تکرارپذیرند و checksum مهاجرت اعمال‌شده را بررسی می‌کنند. مرورگر را روی مبدأ اعلام‌شده در خروجی اجرا باز کنید. مسیرهای `/`، `/docs` و `/docs/openapi.json` قابل دسترسی‌اند. اگر درگاه 5173 اشغال باشد ابزار توسعه ممکن است درگاه بعدی را انتخاب کند؛ `APP_ORIGIN` را مطابق آن اصلاح و فرآیند را دوباره اجرا کنید.

## دستورهای اصلی

| دستور | کارکرد |
| --- | --- |
| `npm run dev` | اجرای توسعه؛ انتخاب محیط از تنظیم فعلی |
| `npm run build:node` | تنظیم Node و ساخت `dist/standalone/server.js` |
| `npm run start:node` | اجرای مستقیم خروجی standalone؛ نیازمند env فرآیند |
| `npm run build` | ساخت پیش‌فرض؛ برای Workers نباید `MVP_RUNTIME=node` باقی مانده باشد |
| `npm start` | اجرای محلی خروجی Workers با Wrangler از طریق `scripts/start-built.mjs`؛ برای Node از start:node استفاده کنید |
| `npm run db:migrate:node` | اعمال مهاجرت‌های ثبت‌شده در journal روی SQLite |
| `npm run db:generate` | تولید مهاجرت از schema با Drizzle Kit؛ خروجی باید بازبینی شود |
| `npm run docs:prepare` | کپی توزیع پین‌شدهٔ Swagger و مجوزهایش در دارایی عمومی |
| `npm run notifications:run` | فراخوانی واقعی کار اعلان با env جاری |
| `npm run typecheck` / `npm run lint` | بررسی TypeScript و ESLint |

`dev` و هر دو فرمان ساخت، آماده‌سازی Swagger را خودکار انجام می‌دهند. `public/docs/swagger/` تولیدشده است و در Git ذخیره نمی‌شود. `npm ci` به‌تنهایی این پوشه را نمی‌سازد؛ برای اجرای مستقیم ابزار چارچوب، ابتدا `npm run docs:prepare` را اجرا کنید. Docker پس از کپی سورس، همین `build:node` را اجرا می‌کند.

## دو محیط اجرا

در Node، `vite.config.ts` بارگذاری `db/index.ts` و `lib/media-storage.ts` را به آداپتورهای Node هدایت می‌کند. Workers از bindingهای `DB` و `BUCKET` استفاده می‌کند. تنظیم میزبانی موجود در `.openai/hosting.json` و افزونهٔ `build/sites-vite-plugin.ts` است. اسکریپت‌های `sites-env*` و `execution-profile.mjs` برای محیط مدیریت‌شدهٔ موجود هستند؛ اجرای معمول Node به تغییر آن‌ها نیاز ندارد.

ساخت و آزمون دو محیط را هم‌زمان اجرا نکنید؛ هر دو `dist` را جایگزین می‌کنند. برای ساخت Workers در shellی که قبلاً Node فعال بوده، ابتدا `unset MVP_RUNTIME` کنید و env/bindingهای مربوط به Workers را مطابق محیط میزبانی تنظیم کنید.

بسته‌های مستقل `tools/` وابستگی، پیکربندی TypeScript و ESLint و آزمون‌های خود را دارند و از بررسی‌های ریشهٔ برنامه خارج‌اند. برای `tools/invara-crawler` نصب و بررسی را از همان پوشه مطابق README آن اجرا کنید؛ CI و ساخت برنامه به نصب Playwright آن بسته وابسته نیستند.

## ورود آزمایشی موجود

فقط در محیط ایزوله، `TEMP_LOGIN_ENABLED=true` و `OTP_SECRET` تصادفی با حداقل ۳۲ نویسه را تنظیم کنید. در `/login` ورود پیامکی، شمارهٔ `09108624707` و سپس کد `123456` را وارد کنید. پیامک واقعی برای این حساب ارسال نمی‌شود. فقط برای همین حساب، کد ثابت پس از انقضا، ارسال مجدد، ورود موفق یا تلاش ناموفق قابل استفادهٔ دوباره است و فاصلهٔ ارسال یا سهمیهٔ درخواست ندارد؛ چالش صادرشدهٔ سرور و فعال‌بودن پرچم همچنان الزامی‌اند. کد کاربران عادی پنج دقیقه اعتبار و پنج تلاش دارد؛ فاصلهٔ ارسال ۳۰ ثانیه و سقف ساعتی پنج درخواست برای هر شماره و بیست درخواست برای هر IP است. شمارهٔ میزبان قدیمی `09108624708` با همین پرچم ورود فوری دارد.

خاموش‌کردن پرچم، درخواست‌های جدید و چالش‌های آزمایشی باقی‌مانده را رد می‌کند، اما نشست صادرشده را خودکار حذف نمی‌کند. اسکریپت `scripts/remove-temp-login-sessions.sql` برای لغو نشست‌های این حساب‌ها موجود است؛ پیش از اجرا مقصد پایگاه داده را بررسی کنید. برای کاربر واقعی، سرویس پیامک لازم است. دادهٔ نمونه (`SEED_SAMPLE_EVENTS`) و عبور از پرداخت (`SKIP_PAY_DEV`) کلیدهای مستقل‌اند و برای آزمون ورود لازم نیستند.

## ناوبری ورود و خوش‌آمدگویی

بازگشت از ورود به مقصد مجاز `next` یا خانه می‌رود؛ مسیر بلیت ابتدا به صفحهٔ عمومی همان رویداد برمی‌گردد تا مهمان دوباره به ورود فرستاده نشود. بازگشت از ثبت‌نام و بازیابی رمز، مقصد پس از ورود و چیدمان خانه را حفظ می‌کند. این بازگشت‌ها مسیر جاری را جایگزین می‌کنند تا صفحه‌های ورود و خوش‌آمدگویی در تاریخچه به یکدیگر اضافه نشوند. در مرحلهٔ کد تأیید، بازگشت ابتدا همان فرم شماره را نشان می‌دهد. پاسخ دیرهنگام درخواست‌های قبلی پس از بازگشت یا خروج از فرم، دیگر فرم را تغییر نمی‌دهد یا مسیریابی نمی‌کند؛ ارسال و ارسال دوبارهٔ کد نیز قفل مشترک دارند تا درخواست هم‌زمان ساخته نشود.

هر سه صفحهٔ خوش‌آمدگویی پیوند «فعلاً رد می‌کنم» دارند که مستقیماً خانه را باز می‌کند و معرفی موقعیت را تکمیل‌شده علامت می‌زند؛ بنابراین خانه دوباره کاربر را به نقشهٔ معرفی نمی‌فرستد. پارامتر معتبر `layout=v1` یا `layout=v2` در این مسیر حفظ می‌شود. آزمون `node tests/auth-navigation.mjs` مقصدهای امن، جلوگیری از حلقهٔ ورود و کنترل ردکردن هر سه صفحه را بررسی می‌کند.

## گردش تغییر

ابتدا مسیر API، منطق مشترک در `lib/`، schema و آزمون مرتبط را بخوانید. در صورت تغییر مدل داده، مهاجرت افزایشی تولید و SQL آن را بررسی کنید؛ مهاجرت اعمال‌شده را ویرایش نکنید. قرارداد API را هم‌زمان در `docs/openapi.json` و توضیح رفتار را در راهنمای مرتبط اصلاح کنید. [آزمون](testing.md) مشخص می‌کند کدام بررسی‌ها مناسب تغییر هستند.
