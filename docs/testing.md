# آزمون، اعتبارسنجی و نگهداری مستندات

برای نسخهٔ فعلی ابتدا `npm run test:discovery` را اجرا کنید. این آزمون قواعد پروفایل مشترک/اینستاگرام، حفظ دادهٔ قبلی و رد رزرو تازه را روی SQLite واقعی و Route Handlerهای واقعی می‌سنجد. آزمون‌های خرید قدیمی در harness کامل، رفتار فعال نسخهٔ اطلاع‌رسانی را توصیف نمی‌کنند؛ برای تغییرات این نسخه از آزمون discovery، مدیریت مستقل، مستندات و آزمون‌های دامنه استفاده کنید.

[فهرست مستندات](README.md)

آزمون مناسب را با مرز تغییر انتخاب کنید. تغییر قرارداد API به بررسی OpenAPI و HTTP نیاز دارد؛ تغییر موجودی/پرداخت به آزمون SQL و یکپارچه‌سازی، و تغییر رابط به بررسی مرورگر. نتایج تاریخی [verification-log](verification-log.md) اثبات وضعیت هر checkout جدید نیستند.

## بررسی مستندات

```sh
npm run test:docs
npm run typecheck
npm run lint
npm run build:node
npm run test:docs:node
npm run test:build-assets
```

`tests/docs.mjs` قرارداد را با Swagger Parser اعتبارسنجی می‌کند، با AST تایپ‌اسکریپت متدهای exportشدهٔ `app/api/**/route.ts` را استخراج و با مسیرهای OpenAPI تطبیق می‌دهد. مسیر جاافتاده، متد اضافه، operationId تکراری، پارامتر مسیر ناقص، خلاصهٔ غیرفارسی، منبع اشتباه و پیوند داخلی خراب باعث شکست می‌شوند. این بررسی وجود عملیات را کنترل می‌کند؛ صحت تمام قواعد ورودی یا تمام نمونه‌های پاسخ را به‌تنهایی اثبات نمی‌کند.

`tests/docs-integration.mjs` از سرور واقعی می‌خواند و HTML فارسی/RTL، برابری قرارداد منتشرشده با فایل مخزن، Content-Type و محتوای JS/CSS، حضور مجوز Swagger و پاسخ صفحهٔ اصلی را بررسی می‌کند. `test:docs:node` و `test:docs:workers` آن را داخل harness ایزولهٔ موجود اجرا می‌کنند؛ از پایگاه دادهٔ تولید استفاده نمی‌کنند.

برای Workers، بعد از پایان بررسی Node:

```sh
unset MVP_RUNTIME
npm run build
npm run test:docs:workers
npm run test:build-assets
```

ساخت‌ها از dist مشترک استفاده می‌کنند و ترتیبی‌اند. دارایی‌های Swagger پیش از dev/build خودکار کپی می‌شوند. اگر مستقیماً ابزار دیگری را اجرا می‌کنید، `npm run docs:prepare` را ابتدا انجام دهید.

## آزمون‌های دامنه

| دستور | پوشش |
| --- | --- |
| `npm run test:sqlite` | SQLite، دامنهٔ رویداد، مهلت ثبت‌نام و تاریخچهٔ رزرو |
| `npm run test:media` | اعتبارسنجی تصویر و پشتیبان رسانه |
| `npm run test:notifications` | اعلان، رمزنگاری و تحویل Push/ایمیل بدون ارسال خارجی |
| `node tests/countdown.mjs` | شمارش معکوس تا شروع و حالت رویداد آغازشده |
| `npm run test:account-checkout` | قواعد حساب و خرید |
| `npm run test:d1-migration` | رفتار مهاجرت در محیط D1 محلی |
| `npm run test:integration:node` | مجموعهٔ کامل HTTP روی ساخت Node |
| `npm run test:integration` | مجموعهٔ کامل HTTP روی ساخت Workers |
| `npm run test:recommendations` | مسیر محدودتر پیشنهادها در harness Workers |
| `npm run test:location-links` | مسیر محدودتر پیوندهای مکان در harness Workers |
| `npm run test:docker` | ساخت و آزمون کانتینر با Docker فعال |
| `npm run test:build-assets` | وجود فایل‌های preload ثبت‌شده در manifest RSC |

آزمون یکپارچه‌سازی به‌طور پیش‌فرض `127.0.0.1:5188` و پایگاه موقت استفاده می‌کند. `TEST_ORIGIN` فقط می‌تواند loopback باشد. برای تست، فقط دادهٔ ایزولهٔ harness استفاده می‌شود؛ ورود آزمایشی و ارسال بیرونی روی تولید را فعال نکنید. بعضی فایل‌های آزمون helper هستند و توسط `tests/integration.mjs` اجرا می‌شوند، نه مستقلاً.

## مرورگر

نمایش `/docs` را روی دسکتاپ و عرض موبایل بررسی کنید: بارگیری ۱۰۳ عملیات، بازشدن مدل‌ها، خوانایی متن فارسی و مسیر LTR، نبود خطای کنسول و کارکرد Execute روی یک GET بی‌اثر مانند سلامت. شمارش صحیح مسیرها به‌تنهایی موفقیت JavaScript در مرورگر را ثابت نمی‌کند.

اسکریپت‌های `tests/visual-*.mjs` مربوط به بررسی گسترده‌تر محصول‌اند و به Playwright، مرورگر و سرور/دادهٔ ایزوله مطابق ورودی خود اسکریپت نیاز دارند. آن‌ها دادهٔ آزمون می‌سازند؛ به پایگاه فعال کاربر اشاره نکنند. درخواست نقشه در خودکارسازی باید کنترل شود.

## تغییر قرارداد

۱. Route و helperهای اعتبارسنجی آن را بخوانید؛ response SQL را هم بررسی کنید، چون type تایپ‌اسکریپت لزوماً تبدیل runtime انجام نمی‌دهد.
۲. متد، پارامتر، schema ورودی/پاسخ، security، statusها و شرح محدودیت را در `docs/openapi.json` اصلاح کنید. برای هر عملیات `x-source` مسیر واقعی فایل است.
۳. فهرست مسیرها و قواعد مرتبط در `docs/api.md` و راهنمای دامنه را هماهنگ کنید. متن‌ها فارسی و شناسه‌های ماشینی مطابق کد بمانند.
۴. بررسی ساختاری، نوع، lint، ساخت و آزمون HTTP محیط مربوط را اجرا کنید. تغییر مشترک باید در هر دو runtime بررسی شود.

OpenAPI از کد تولید خودکار نمی‌شود؛ فایل JSON مرجع مستندات است و Route آن را مستقیم import می‌کند. هیچ نمونهٔ واقعی حساب، کوکی، کلید سرویس، QR یا کلید اسکنر را در آن ثبت نکنید.

آزمون پنل مستقل: پس از ساخت Node، `npm run test:fast:node`؛ پس از ساخت Workers، `npm run test:fast:workers`. هر دو روی پایگاه و رسانهٔ موقت اجرا می‌شوند. [پوشش کامل](fast-admin.md).

`npm run test:fast-organizers` مهاجرت نام برگزارکننده را روی پایگاه پرشده بررسی می‌کند و Route Handlerهای واقعی را مستقیماً با Request و SQLite موقت اجرا می‌کند؛ هیچ سرور برنامه‌ای راه‌اندازی نمی‌شود. نام مستقل، جست‌وجو، حساب مجاز، بلیت/برنامه، قفل رزرو، دسترسی و نظارت نظر پوشش داده می‌شوند. `npm run test:d1-migration` حفظ روابط در همین مهاجرت را روی D1 محلی بررسی می‌کند؛ این فرمان فقط محیط پایگاه آزمون را اجرا می‌کند.

`npm run test:fast-editor-rsc` خروجی واقعی `fastEvent` و `fastOrganizers` را با رده‌های بلیت و گالری در React Flight سریال می‌کند. هر دو نوع برگزارکننده آزموده می‌شوند؛ هیچ سرور برنامه‌ای اجرا نمی‌شود. این آزمون بخشی از `test:sqlite` است و خطای عبور ردیف‌های دارای prototype تهی از مرز Server/Client را پوشش می‌دهد؛ موفقیت JSON API به‌تنهایی این خطا را آشکار نمی‌کند.

`npm run test:event-sync` مهاجرت پرشده، ۵۱ ردیف واقعی شیت، رسانهٔ واقعی، idempotency، هم‌زمانی، restart، خطای منبع/تصویر، توقف انتشار و مجوزها را می‌سنجد. fixtureها snapshot دادهٔ عمومی منبع هستند؛ transport آزمون کنترل‌شده است و دادهٔ برنامه/پایگاه موقت واقعی می‌ماند. [پوشش و راه‌اندازی](event-sheet-sync.md).
